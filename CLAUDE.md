# Fog Scout – Projektkontext für Claude Code

Map-Overlay für Dead by Daylight (Windows). Erkennt beim Match-Start den Map-Namen per OCR und blendet die passende Callout-Karte aus `maps/` als klickdurchlässiges Overlay ein. Außerdem: Ausblenden nach der Runde bzw. Pause in Menüs, und ein Tab „Server“ zur Regionswahl über die hosts-Datei und Anzeige des verbundenen Spielservers (Ideen von „Make Your Choice“). Oberfläche und Log: **Deutsch und Englisch** (`i18n.py`, Einstellung `ui_language`, „auto“ = Windows-Sprache). Doku: Deutsch (`README.md`) + Englisch (`README.en.md`). Code und Kommentare: Englisch.

**Name:** bis 1.8.91 „DbD Map Scout“ (Paket `dbdmapscout/`, Repo `dbd-map-scout`), seit 1.9 **Fog Scout** (Paket `fogscout/`; Repo seit 1.9.1 `sarujansa/fog-scout`, GitHub leitet die alte Adresse um – `update.py` braucht nichts), weil ein anderes Programm denselben Namen trägt. Was den alten Namen trug, wird einmal übernommen: `rename.migrate` beim Start (Crash-Dateien/Log, leerer alter Paketordner mit `__pycache__`), `autostart` (alte Aufgaben + Verknüpfungen + altes Icon weg, `SETUP_VERSION` 6), `hostsedit` (`OLD_BEGIN`/`OLD_END` = eigener Abschnitt, `OLD_BACKUP_SUFFIX` = Original), `obsrec` (`OWN_SOURCES` per `SetInputName` von `OLD_SOURCE_NAME` umbenannt, `OLD_INDEX`/`OLD_CLIPS_INDEX` per `adopt_old_file`), `official` (`OLD_PREFIX`/`OLD_FORMAT` weiter gelesen, Userscript 5 liest `OLD_LAST_KEY`), `update._version` liest beide Paketpfade. Bewusst unverändert: Umgebungsvariablen `DBDMS_*` (unsichtbar; `DBDMS_UPDATED` muss über den Neustart von `start.bat` hinweg gleich heissen), `settings.json`/`rounds.jsonl`/`official.jsonl`. `HISTORY.md` behält die alten Pfade. Das GitHub-Repo hat der Nutzer nach dem Merge von 1.9 umbenannt.

## Harte Regeln (nicht verhandelbar)

Das Programm muss „regelkonform“ zu Dead by Daylight bleiben. Konkret:

- **Keine Eingaben ans Spiel** (kein SendInput, keine Tastatur-/Maus-Simulation, keine Automatisierung).
- **Kein Zugriff auf den Spielprozess** – nicht einmal `OpenProcess`, kein Speicherlesen, keine Injection, keine Modul-/Handle-Abfragen mit PID.
- **Keine Spieldateien** lesen oder schreiben (auch nicht `GameUserSettings.ini`, Splash-Screen, Movies).
- Erlaubt sind nur: **Bildschirmpixel** (mss/BitBlt) und – nur solange DBD im Hintergrund ist – die **Fensteraufnahme per Windows Graphics Capture** (wie OBS „Fensteraufnahme“, Bild kommt vom Windows-Compositor; `wincapture.py`, Bibliothek windows-capture **2.0.1 fest**, geprüft: importiert kein OpenProcess/GetWindowThreadProcessId/Hooks/Eingaben – bei Versionswechsel erneut prüfen; nie `PrintWindow`, das schickt Nachrichten ans Spiel), Fensterinfos (Titel, Klasse `UnrealWindow`, Position über EnumWindows), **Mauszeiger-Status** (`GetCursorInfo`, wie OBS), die **Windows-hosts-Datei** (nur Tab „Server“, nur GameLift-Namen) und **Paketköpfe des Netzwerkverkehrs** (nur Tab „Server“, Anzeige „Verbunden mit“; vom Nutzer ausdrücklich gewünscht, wie in Make Your Choice). Seit 1.42 außerdem **Systemwerte** (vom Nutzer gewünscht): `GetSystemTimes`/`GlobalMemoryStatusEx`, NVIDIA `nvml.dll` nur aus System32/NVSMI (Programm läuft als Admin – nie aus dem aktuellen Ordner laden), nur Gerätewerte (Temperatur, Last, Speicher, Leistung; **nie** die NVML-Prozesslisten mit PIDs), CPU-Temperatur nur aus dem Shared Memory von HWiNFO (`Global\HWiNFO_SENS_SM2`, nur lesen; seit 1.2.2 auf ausdrückliche Entscheidung des Nutzers auch die **FPS**, die HWiNFO dort selbst ablegt – HWiNFO misst sie per PresentMon (Windows-Ereignisse) oder RivaTuner; das Programm liest nur das Shared Memory, nie das Spiel) – **kein eigener Treiber** (WinRing0/LibreHardwareMonitor ausgeschlossen: Anti-Cheat, Microsoft-Sperrliste). Beim Mitschnitt: nur IPv4/UDP-Kopffelder (Adressen, Ports) lesen, **nie Paketinhalte**, nichts senden, nichts speichern außer der temporären Ergebnisdatei (Server-IP **nicht** ins Logfile, nur die Region), kein Treiber (Raw-Socket `SIO_RCVALL`), **nur Modus `RCVALL_IPLEVEL`** (eigener Verkehr; nie `RCVALL_ON`/Promiscuous, auch nicht als Rückfall), keine Zuordnung über die PID des Spiels. Seit 1.64 außerdem die **Windows-Mediensteuerung** (vom Nutzer gewünscht, „Läuft gerade“ im Balken): nur Titel/Interpret/Wiedergabestatus, Fortschritt (Timeline: Position/Länge, seit 1.64.7) und das Cover (Thumbnail, nur im Speicher, ≤ 4 MB, einmal je Titel) der aktuellen Sitzung über `GlobalSystemMediaTransportControlsSessionManager` (pywinrt **3.2.1 fest**: winrt-runtime, -Windows.Foundation, -Windows.Media.Control, -Windows.Storage.Streams; geprüft: importiert kein OpenProcess/Hooks/Eingaben – bei Versionswechsel erneut prüfen) – **nie steuern** (kein Play/Pause/Skip), nichts speichern, Titel nie ins Log/die Diagnose.
- **onnxruntime-Telemetrie aus** (seit 1.64.7, im Container gemessen: onnxruntime ≥ 1.29 sendet von sich aus an `mobile.events.data.microsoft.com/OneCollector`, auch unter Linux; `disable_telemetry_events()` allein hilft nicht): `fogscout/__init__.py` setzt `ORT_DISABLE_TELEMETRY=1`, bevor irgendein Modul onnxruntime lädt – nie entfernen (daneben seit 1.8.38 `OPENBLAS_NUM_THREADS=1` per `setdefault`: sonst warten die BLAS-Threads zwischen den Blicken aktiv, gemessen 46 % → 4 % eines Kerns im Menü; Test `test_numpy_does_one_thread_so_nothing_spins_between_the_looks`); bei neuen Bibliotheken auf eingebaute Telemetrie achten (Test `test_onnxruntime_telemetry_is_off_before_it_is_loaded`).
- Map-Erkennung und Overlay bauen **keine Internetverbindung** auf (Ausnahme nur für Updates, auf Wunsch des Nutzers: im Starter `start.bat` → `update.py` per `git fetch` von GitHub, abschaltbar; im Programm **nur auf Klick** „Jetzt nach Updates suchen“ – `update.check()`, nur `git fetch` von GitHub, installiert nichts; installiert wird immer im Starter nach Neustart); nur der Server-Tab pingt AWS-GameLift (UDP 7770 / ICMP) und löst DNS auf (auch Reverse-DNS der Spielserver-Adresse). Während „Verbunden mit“ läuft, alle 5 s ein Ping an die verbundene Region (`gamelift.<region>.amazonaws.com` per ICMP, sonst Beacon `gamelift-ping.<region>.api.aws`) – **nie Pakete an den Spielserver selbst**.
- **Offizielle Match-Daten (Kills/Escapes/BP in der Statistik, seit 1.34, vom Nutzer so freigegeben):** Die Daten lädt der **Browser** des Nutzers: eigenes Userscript `fogscout/matchexport.user.js` (Tampermonkey & Co., `@grant none`) liest auf stats.deadbydaylight.com nur die Antwort, die die Seite selbst lädt (`account-backend.bhvr.com/player-stats/match-history/games/dbd/…`, gefunden über das MIT-Userscript „DBD Detailed Match History“), macht **keine eigenen Anfragen**, gibt nur Whitelist-Felder weiter (keine Login-/Kontodaten, keine Namen/IDs anderer Spieler) und lädt sie als `fogscout-matches.json` in den Download-Ordner (nur wenn ein neues Match dabei ist). Seit 1.8.46 auf Klick („Aufbau der Match-Daten speichern“, vom Nutzer freigegeben) einmal zusätzlich `fogscout-structure.json` mit nur dem **Aufbau** der Antwort – Feldnamen und Typen, nie Werte, Schlüssel, die keine Bezeichner sind, als `<key>`; weitere Felder übernimmt das Userscript erst nach Freigabe des Nutzers – seit 1.8.48 (Version 3, freigegeben: „Eigene Daten“ + „Match-Infos“) zusätzlich Spielmodus/Event/Map-ID/Gesamtdauer und **nur vom eigenen Spieler** Loadout (Perks, Add-ons, Opfergabe, Kraft/Item; id + Name, keine Bilder), Embleme, Punktekategorien (`DBD_*ScoreCat_*`), Prestige/Level, `killerMatchStatus`; von anderen Spielern weiter nur Charakter/Rolle/Status (Gegner-Loadouts/Prestige/Plattform bewusst nicht freigegeben). Das Programm liest nur Dateien `fogscout-matches*.json` **mit** der Kennung `format: fogscout-matches` und **löscht sie danach** (Bedingung des Nutzers); fremde Dateien bleiben liegen. Auf Wunsch (`official_open_after_dbd`, Standard aus) öffnet das Programm die Seite per `webbrowser.open` im Standardbrowser, nachdem DBD ≥ 15 s geschlossen ist und eine Runde gespielt wurde – **nie während DBD läuft**. Bewusst nicht: Login/Token im Programm, Cookies aus dem Browser lesen, lokaler Server/Port (Programm läuft als Admin), eigene API-Abrufe.
- **Aufnahmen mit OBS (seit 1.4, vom Nutzer ausdrücklich freigegeben):** das Programm spricht per **obs-websocket 5** mit OBS – **nur** auf `127.0.0.1` (`obsrec.HOST`, fest, nie einstellbar; Port/Passwort aus den Einstellungen), eigener Minimal-WebSocket-Client nur aus der Standardbibliothek. Es sagt OBS nur *wann*: `StartRecord` beim Map-Banner (davor `SaveReplayBuffer`, falls der Puffer läuft = Vorlauf), `StopRecord` beim Rundenende, `SetRecordDirectory` auf den gewählten Ordner. Aufnehmen tut OBS; empfohlen Fenster-/Bildschirmaufnahme, **nicht** die Spielaufnahme (hängt sich in den Spielprozess – unser Programm fasst DBD weiter nicht an). Gelöscht werden nur Dateien aus dem eigenen Index `fogscout-recordings.jsonl` im Aufnahmeordner (seit 1.8.23 auch Farming-Aufnahmen nach `rec_farming_days`, nie behaltene/markierte) bzw. (seit 1.8.13) aus `Clips/fogscout-clips.jsonl` und ältere Clips, die das Programm an ihrem eigenen Namensmuster erkennt – nie fremde. Kein Upload (Cloud nur über einen synchronisierten Ordner des Nutzers). Seit 1.4.2 **ffmpeg** (Binary aus `imageio-ffmpeg` **0.6.0 fest**, BSD-2, keine Abhängigkeiten; `obsrec.ffmpeg_exe()` nimmt nur das pip-installierte, nie PATH) als Kindprozess **nur auf den eigenen Aufnahmedateien** (Vorlauf + Runde → eine Datei, `-c copy`, kein Netz, kein Fenster) – nie auf Spieldateien. Seit 1.6 (vom Nutzer freigegeben: „nur DBD- und Discord-Ton, einzeln abschaltbar“) außerdem `GetInputList`/`GetCurrentProgramScene`/`CreateInput` (Art `wasapi_process_output_capture` = OBS-eigene Anwendungs-Audioaufnahme, Fenster per Exe-Name `AUDIO_APPS`, Priorität 2) und `SetInputMute`/`GetSpecialInputs` (Desktop-Audio, Mikrofon) – die Audioaufnahme macht OBS über Windows-Process-Loopback, das Programm schickt nur die Anfragen und kennt keine PID; F8-Sofort-Clip: `SaveReplayBuffer`, ffmpeg `-sseof -n -c copy` nach `Clips/`, danach wird die gespeicherte Replay-Datei gelöscht (eigene Datei: auf unsere Anfrage erzeugt, Pfad von OBS – wie der Vorlauf beim Zusammenfügen). Seit 1.9 `SetInputName` nur für die **eigenen** vier Quellennamen, die OBS noch unter dem alten Programmnamen „DbD Map Scout“ hält (`Recorder._input_names`, einmalig; nie Quellen des Nutzers). Seit 1.8.18 (Nutzer: „Discord hört man gar nicht“) außerdem `GetSceneItemList` (lesen) und `CreateSceneItem`/`SetSceneItemEnabled` nur für die **eigenen** Tonquellen und nur, wenn deren Häkchen an ist (`Recorder._in_scene`: Anwendungs-Audio nimmt OBS nur in der laufenden Szene auf; Gruppen/verschachtelte Szenen nicht durchsucht). Seit 1.8.20 (Nutzer spielt über Epic, Spiel-Spur still – die Quelle suchte die Steam-Exe) `GetInputPropertiesListPropertyItems` (Fensterliste, die **OBS** für die eigene Quelle anbietet, nur lesen) + `GetInputSettings`/`SetInputSettings` nur auf den eigenen Quellen: `Recorder._follow_window` wählt den Eintrag, dessen Exe `WINDOW_EXES` passt (DBD Steam/Epic, Discord/PTB/Canary). Seit 1.8.5/1.8.6 (Nutzer: „Discord-Audio aus den Clips entfernen“ → „wie bei Medal“) auch `SetInputAudioTracks` (jede Quelle auf Spur 1 + eigene Spur: nur DBD 2, Discord 3, Mikrofon 4; seit 1.8.19 – Nutzer: „wirklich nur DBD und Hintergrundprogramme separat“ – alle **übrigen** Tonquellen in OBS per `GetInputAudioTracks` geprüft und von Spur 2–4 auf Spur 5 „Hintergrund“ gelegt, Spur 1/6 bleiben; Desktop-Ton nur Spur 1, weil er DBD und Discord enthält; `SOURCES` + `other`, `REC_TRACKS_NEEDED` 0b11111) und `GetProfileParameter` (nur **lesen**: Output/Mode, AdvOut/RecTracks – das Profil wird nie geändert, nur ein Hinweis gezeigt). Seit 1.8.41 (Nutzer: „dass das Programm es selber macht mit der Fenstererkennung und im OBS hinterlegen“, Häkchen `rec_window`, Standard aus) außerdem eine **eigene Bildquelle** `WINDOW_SOURCE` der Art `window_capture` (OBS-Fensteraufnahme über Windows Graphics Capture, `method` 2, Priorität 0 = „Titel, sonst Fenster desselben Typs“ = Klasse `UnrealWindow`, Steam/Epic/Store gleich; **nie** `game_capture`, die hängt sich ins Spiel): `CreateInput` in der laufenden Szene, `GetVideoSettings` + `SetSceneItemTransform` (einmal auf die Leinwand eingepasst), `CreateSceneItem`/`SetSceneItemEnabled` nur für diese eigene Quelle (aus = nur ausgeblendet, nie gelöscht; die Bildschirmaufnahme des Nutzers wird nie angefasst), `_follow_window` auf die laufende Exe. Solange DBD läuft, richtet `Recorder._recheck` alle `RECHECK_S` = 30 s erneut ein, falls OBS beim DBD-Start nicht bereit war. Seit 1.8.47 (Nutzer: „OBS Autostart“, gewählt: beim DBD-Start, OBS bleibt danach offen; Häkchen `rec_obs_start`, Standard aus) **startet das Programm OBS selbst**, wenn es beim DBD-Start nicht erreichbar ist: `obs64.exe --minimize-to-tray` im eigenen Ordner, nur aus dem Registry-Ordner `HKLM\SOFTWARE\OBS Studio` bzw. `Program Files\obs-studio` (absolut, nie PATH/aktueller Ordner), nur wenn kein OBS-Hauptfenster offen ist (`capture.top_windows`, nur Titel/Klasse), höchstens einmal je DBD-Start (`_obs_started`), danach alle `OBS_START_POLL_S` bis `OBS_START_WAIT_S`; OBS wird nie beendet. `StartReplayBuffer` höchstens **einmal je DBD-Start und OBS-Sitzung** (`_start_buffer`, seit 1.8.42: jeder gescheiterte Start öffnet in OBS einen Fehlerdialog); läuft der Puffer danach nicht, einmal `BUFFER_FAILED` im Programm. Eine geänderte `Config` bei laufendem DBD richtet OBS beim nächsten Leerlauf (≤ 5 s) neu ein. Seit 1.8.89 (Nutzer: „nur das DBD-Fenster aufnehmen und das Overlay im Spiel“, Häkchen `rec_overlay`, Standard aus, nur zusammen mit `rec_window`) eine **eigene Bildquelle** `OVERLAY_SOURCE` der Art `image_source` auf die **eigene Datei** `cache/obs-overlay.png` (`obsoverlay.Writer` schreibt das sichtbare Overlay als PNG) über der Fensterquelle: `CreateInput`/`CreateSceneItem`/`SetSceneItemEnabled`/`GetInputSettings`/`SetInputSettings` nur für diese Quelle, `GetSceneItemList` (lesen) + `SetSceneItemTransform` nur auf dem eigenen Item (`obsoverlay.overlay_transform` aus dem Transform des Fenster-Items) – nie Quellen des Nutzers, nichts gelöscht.
- **Discord Rich Presence (seit 1.7, vom Nutzer ausdrücklich freigegeben, Standard aus):** `discordrpc.py` spricht nur mit dem **lokalen Discord-Client** über dessen IPC-Pipe `\\?\pipe\discord-ipc-N` (derselbe Weg wie bei Spielen mit Rich Presence; nur Standardbibliothek, kein Internet, kein Prozesszugriff – wie OBS über obs-websocket). Gesendet werden nur `details`/`state` (Map, Rolle, Killer, Lobby-Zustand) und die Startzeit mit der **eigenen** PID (Discord verlangt sie für die Zuordnung; nie die PID des Spiels). Braucht eine **Application-ID**, die der Nutzer im Discord-Developer-Portal anlegt (`discord_client_id`); ohne ID wird nichts gesendet. Keine Buttons/Bilder (die holt Discord aus dem Internet), nichts aus Discord lesen außer den Antworten.
- **Spotify „Als nächstes“ (seit 1.8, vom Nutzer ausdrücklich freigegeben – „ja“ nach Hinweis auf Internet + Login; Standard aus):** die Windows-Mediensteuerung kennt nur den laufenden Titel, die Warteschlange kommt aus der **Spotify Web API** (`spotify.py`, nur Standardbibliothek): `GET /me/player/queue` alle `POLL_S` = 30 s (seit 1.8.36, vorher 10 s) bzw. sofort beim Titelwechsel und noch einmal nach `REREAD_S` = 5 s (seit 1.8.37: direkt nach einem Wechsel antwortet Spotify noch mit der alten Liste); 429 mit `QUOTA_EXCEEDED` (Kontingent je Entwicklerkonto seit Juli 2026) → Statuszeile + Pause ≥ `QUOTA_WAIT_S`, 429 ohne Retry-After → verdoppelnde Wartezeit, nur solange die Musikkarte aktiv ist und DBD läuft; Scopes `user-read-playback-state user-read-currently-playing`; **nur lesen**, nie Play/Pause/Skip, nichts anderes vom Konto. Anmeldung per OAuth 2 **PKCE** (ohne Client-Secret) mit einer App, die der Nutzer im Spotify-Developer-Dashboard anlegt (`spotify_client_id`); Redirect auf `REDIRECT_URI` = `http://127.0.0.1:27831/callback` – dafür hört `LoginServer` **nur während der Anmeldung** (≤ `LOGIN_WAIT_S` = 180 s) einmal auf diesem Port, nimmt nur `/callback` mit passendem `state` an und schließt danach (die einzige Ausnahme von „kein lokaler Port“ – seit 1.10 nutzt der YouTube-Login denselben `LoginServer` auf einem freien Port; ohne Listener müsste der Nutzer die Adresse aus dem Browser abtippen). Gespeichert wird nur das Refresh-Token, mit Windows-DPAPI verschlüsselt (`protect`/`unprotect`, `spotify_token` in `LOCAL_KEYS`), „Spotify-Verbindung trennen“ löscht es. Die Liste erscheint nur, wenn Spotifys aktueller Titel dem der Mediensteuerung entspricht (`spotify.matches` über `same_title`, seit 1.8.37 auch bei anderer Schreibweise: Klammern, „ - Remaster“, „feat.“; sonst spielt ein anderer Player) oder – Sitzung von Spotify selbst – die Liste nach Beginn des Lieds gelesen wurde (`app_spotify.SONG_LAG_S`). Titel nie ins Log/die Diagnose.
- **YouTube-Upload (seit 1.10, vom Nutzer ausdrücklich freigegeben – „ich zahle für YouTube … Clips immer hochladen, bestimmte Videos per Rechtsklick“ – und damit die einzige Aufhebung von „kein Upload“; Häkchen `youtube_on` Standard aus, die Warteschlange läuft auch bei Aus, solange etwas drin ist):** `ytupload.py` spricht nur mit Google (`ENDPOINTS`: `accounts.google.com`/`oauth2.googleapis.com` für OAuth 2 PKCE mit Client-ID **und** Client-Secret des vom Nutzer selbst angelegten OAuth-Clients „Desktop-App“ – Google verlangt das Secret auch bei PKCE, behandelt es bei Desktop-Clients aber nicht als vertraulich; `www.googleapis.com/upload/youtube/v3/videos` für den fortsetzbaren Upload; Scope `youtube.upload` – seit 1.11 mit Häkchen `youtube_playlists` (vom Nutzer freigegeben, Standard aus) zusätzlich `SCOPE_MANAGE` = `youtube` („YouTube-Konto verwalten“), genutzt **nur** für `playlists.list` (eigene Playlists auflisten, `ENDPOINTS["playlists"]`) und `playlistItems.insert` (das eben hochgeladene Video in die gewählte Playlist, `ENDPOINTS["items"]`); ohne Häkchen fragt der Login ihn nicht an, ein alter Login ohne ihn lädt weiter hoch und meldet nur den fehlenden Playlist-Schritt), nur Standardbibliothek. Gesendet werden nur Dateien aus dem Aufnahmeordner (`Job.rel`: Clips aus F8/Editor automatisch bei Häkchen, Runden **nur** per Rechtsklick/Knopf „Auf YouTube hochladen“) plus Titel/Beschreibung aus Map, Rolle/Killer, Zeit (`describe` – nie Spielernamen), gelesen nur die Antworten (Video-ID). Login über `spotify.LoginServer` auf einem freien Port (Google erlaubt jeden Loopback-Port), Refresh-Token und Client-Secret DPAPI-geschützt (`SECRET_KEYS`/`LOCAL_KEYS`). Uploads **pausieren ab der Lobby** (`App._youtube_tick` → `set_paused(_yt_pause_wanted())`: Runde läuft **oder** DBD-Fenster da und Lobby-Zustand nicht idle – seit 1.11.2, vorher erst ab Banner: kein Bandbreitenfressen beim Verbinden und im Match), laufen in `CHUNK`-Stücken mit `Content-Range` (308 = weiter; `resume_point` nach Pause/Neustart, Session-URI in `youtube_queue`), Kontingent `Quota` (Google: 10 000 Einheiten je Projekt und Tag, 1 600 je Upload = 6, Tag wechselt 08:00 UTC ≈ Pazifik-Mitternacht, `quotaExceeded` = Tag verbraucht – Rest wartet, nichts geht verloren). Die lokale Datei bleibt immer; Video-ID in den Index (`Recorder.set_link`, Feld `yt`), Link per Rechtsklick. Diagnose nur Zustand/Zähler, nie Secret oder Token.
- Neue Features, die gegen diese Regeln verstoßen würden: nicht umsetzen, sondern nachfragen.

## Setup des Nutzers (wichtig für Tests und Schwellenwerte)

- Monitor Samsung G5, **3440×1440**; DBD **meistens über Steam**, manchmal über Epic oder den Microsoft Store (Nutzer, 1.8.20 – alle drei müssen gehen: Exe `DeadByDaylight-Win64-Shipping.exe` / `-EGS-Shipping.exe` / `-WinGDK-Shipping.exe`) im Modus **Fenster-Vollbild**.
- DBD rendert **16:9 = 2560×1440 zentriert**, schwarze Balken links/rechts je 440 px. Alle UI-Positionen daher relativ zum 16:9-Viewport rechnen (`detector.viewport()`), nie relativ zur vollen Fensterbreite.
- Spielsprache Englisch (EN/DE sind standardmäßig aktiv). Spielt oft Killer, auch Custom Games mit Bots.
- Overlay-Standardposition „automatisch“ = im linken schwarzen Balken.

## Starten, Testen

```bat
start.bat                 :: legt beim 1. Mal .venv an und installiert requirements.txt
start_debug.bat           :: mit Konsole
.venv\Scripts\python -m fogscout                         :: normal
.venv\Scripts\python -m fogscout --simulate ORDNER       :: spielt Screenshots statt Bildschirm ab (0,8 s/Bild)
.venv\Scripts\python -m fogscout --test BILD.png ...     :: Banner-Erkennung auf Screenshots
.venv\Scripts\python -m pip install pytest
.venv\Scripts\python -m pytest -q tests
```

- Tests immer laufen lassen nach Änderungen an `detector.py`, `matchend.py`, `hostsedit.py`, `regions.py`, `netwatch.py`, `connwatch.py`, `roundtimer.py`, `wincapture.py`, `official.py`, `matchexport.user.js` (der Test führt das Userscript mit `node` aus, ohne node übersprungen).
- Python: nur **3.12–3.14** (seit 1.8.50: für 3.15 fehlen Windows-Pakete von onnxruntime und pywinrt 3.2.1; numpy erst ab 3.12). Die Ersteinrichtung in `start.bat` fragt den Launcher gezielt `py -3.14`/`-3.13`/`-3.12`, sonst `python` nur im selben Bereich, und baut ein halbfertiges `.venv` neu; bei einer neuen Python-Version erst die Wheels aller Pakete prüfen, dann den Bereich in `start.bat`, README und `tests/test_start_bat.py` gemeinsam anheben.
- Pakete: seit 1.8.53 **alle Versionen fest** (`==`, auch die Abhängigkeiten von onnxruntime; Wächter `test_every_package_is_pinned_to_a_tested_version`) – anheben nur nach Prüfung der Windows-Wheels für 3.12–3.14 und Tests. `update.py --deps` (von `start.bat` bei jedem Start) installiert `requirements.txt` bzw. `requirements-extra.txt` neu, sobald sich die Datei geändert hat (SHA-256 in `.venv\*.sha256`). Für die Tests lokal `pip install imageio-ffmpeg==0.6.0` (sonst wird der echte-ffmpeg-Test übersprungen). `requirements-extra.txt` (windows-capture) immer mit `--no-deps`: das Paket verlangt `opencv-python`, das Projekt nutzt `opencv-python-headless` – beide zusammen zerstören `cv2`.
- Update beim Start: `update.py` (nur Standardbibliothek, als Skript aufgerufen) zieht auf `main` per Fast-Forward nach – nie bei eigenen Änderungen, anderem Zweig, eigenen Commits, offline. Exit-Code 3 = aktualisiert → `start.bat` startet sich **in derselben Zeile** neu (cmd liest .bat-Dateien während der Ausführung weiter; eine geänderte `start.bat` darf nicht an alter Byte-Position weitergelesen werden). Diese Zeile nicht aufteilen. Ergebnis in `.venv\update_status.txt`, die App zeigt es im Log.
- GitHub Actions (`.github/workflows/tests.yml`) führt pyflakes + pytest bei jedem PR unter Linux aus und pytest zusätzlich unter Windows (`tests/test_windows.py`: natives Overlay, Hinweisfenster, Hotkeys, windows-capture 2.0.1 – nur dort ausgeführt) – PRs erst mergen, wenn der Haken grün ist. Seit Okt. 2026 (öffentliches Repo, vom Nutzer eingeschaltet) zusätzlich in GitHub: **CodeQL** (Default-Setup, Python/JavaScript/Actions – sein Check muss ebenfalls grün sein, Funde einzeln prüfen), **Secret Protection + Push protection**, **Dependabot alerts** (keine Dependabot-PRs: Versionen hebt nur eine geprüfte Änderung an, siehe Pakete). Ein Lauf, der nach wenigen Sekunden ohne Runner endet (`runner_id` 0, keine Schritte/Logs – Actions-Kontingent des damals privaten Repos), ist **nicht** grün: so lief die Windows-Prüfung von 1.8.1 bis 1.8.37 unbemerkt nicht (1.8.37 repariert).
- Tests dürfen **niemals die echte hosts-Datei** anfassen (unter Windows schlägt `tests/conftest.py` jeden Test fehl, der `hostsedit.hosts_path()` erreicht; Schreibtests sind dort mit `only_linux_hosts` übersprungen). `hostsedit.hosts_path()` ignoriert die Test-Variable `DBDMS_HOSTS_FILE` unter Windows absichtlich (Sicherheit des Admin-Helfers) – Schreibtests laufen daher nur über `hostsedit.build()` / `apply_job` mit reinen Text-/Temp-Dateien bzw. unter Linux/CI. Nicht „reparieren“.
- `settings.json`, `fogscout.log`, `diagnose.txt`, `fogscout-crash.txt`, `fogscout-crash-last.txt`, `debug/`, `rounds.jsonl`, `official.jsonl`, `backup/`, `user_maps/`, `cache/` sind Laufzeitdateien, nicht committen.

## Wichtige Designentscheidungen (nicht ohne Grund ändern)

- **Erkennung**: nicht Text raten, sondern für jeden bekannten Namen die Wahrscheinlichkeit berechnen (Lexikon-Scoring) und über mehrere Frames kombinieren. Unbekannter Text darf nie auf eine falsche Map abgebildet werden.
- **Rundenende – Fehlalarme sind schlimmer als verpasste Erkennungen.** Ein Overlay, das mitten im Match verschwindet, ist der schlimmste Fehler. Darum:
  - Screen-Hinweise brauchen 2 Blicke in Folge (CONTINUE mit sehr gutem Fit: 1), Ladebildschirm 3 Blicke **und** stilles Bild **und** fast schwarzes Bild (`detector.is_dark`, ≥ 85 % der oberen 70 % unter Grau 12; gemessen: Ladebildschirm 0,95, dunkelstes Spielbild 0,75) – ohne „dunkel“ beendete am Boden liegen (geslugged: Aufsteh-Balken + fast stilles Bild) die Runde (1.31.3, Ironworks of Misery). Testbilder `tests/data/end/`.
  - Mauszeiger-Hinweis erst nutzen, wenn beim Map-Banner der Zeiger nachweislich versteckt war (`cursor_proven`).
  - Menü-Latch zählt nur Zeit, in der DBD aktiv und der Zeiger sichtbar ist (60 s).
  - Regionen nie in die schwarzen Balken ausdehnen (FPS-Anzeigen, Benachrichtigungen). Ausnahme: `detector.fills_bars()` – Ergebnisbildschirm, Lobby und Menüs nutzen auf Ultrawide die **volle Fensterbreite** (CONTINUE und Währung sitzen am echten rechten Rand, x ≈ 2800–3300). Nur wenn beide Balken selbst Bild enthalten (im Match sind sie schwarz), reichen CONTINUE-/Währungsregion bis zum Fensterrand.
  - Eigenes Overlay wird vor jeder Auswertung aus dem Bild geschwärzt (`worker._mask_overlay`).
- Events mit `gen` (Map-Generation) – veraltete `menu`/`match_end` für eine alte Map werden ignoriert.
- hosts-Datei: latin-1 lesen/schreiben (byte-genau), nur an LF splitten, Backup `hosts.fogscout-backup` vor der ersten Änderung, Fremdeinträge (Make Your Choice) werden ersetzt. Ergebnisdatei wird vom normalen Prozess vorab angelegt (sonst nach Admin-Schreiben nicht lesbar).
- Bewusst **nicht** umgesetzt: Firewall-Modus, Spieldatei-Änderungen, Dead-by-Queue-API. („Verbunden mit“ per Paketköpfen ist seit 1.5.0 drin, auf Wunsch des Nutzers.)
- Make Your Choice ist GPL-3.0: **keinen Code daraus übernehmen**, nur eigene Umsetzungen. Karten-/Realm-Namen stammen aus LucaFontanot/dbd-map-overlay (Apache-2.0), siehe `THIRD_PARTY.md`.

## Engineering-Regeln (öffentliches Repo, Nutzer 1.8.51)

Das Repository ist **öffentlich**: Code, Git-Historie, Workflows und Doku liest jeder. Gilt zusätzlich zu den harten Regeln oben (die gehen vor).

- **Erst lesen, dann ändern.** Sprache, Framework, Befehle nie annehmen, sondern im Repo prüfen; bestehenden Konventionen folgen; kleine, prüfbare Änderungen statt Umbau; Schnittstellen und Verhalten erhalten oder die Änderung begründen; keine fremden Änderungen und kein spekulatives Refactoring; scheinbar toten Code erst nach Prüfung dynamischer Bezüge entfernen; neue Abhängigkeiten nur mit klarem Nutzen (Bibliotheken mit Systemzugriff wie bisher Version fest + geprüft).
- **Nichts erfinden.** Test-, Mess-, Coverage- und Sicherheitsergebnisse nur aus tatsächlich ausgeführten Befehlen; bestätigte Fehler von Vermutungen trennen; „schneller/sicherer/korrekt“ nur mit Beleg. Fehlgeschlagene, übersprungene oder nicht ausgeführte Prüfungen ausdrücklich nennen; Tests nie abschwächen, um grün zu werden; für bestätigte Fehler einen Regressionstest.
- **Performance.** Pfad und Engpass benennen → Ausgangswert messen (profilieren vor komplexen Optimierungen) → kleinste begründete Änderung → Tests → unter vergleichbaren Bedingungen erneut messen (CPU, Speicher, Latenz, Startzeit). Absolute Werte plus Prozent – niedriger besser: (alt − neu) / alt · 100, höher besser: (neu − alt) / alt · 100 – mit Umgebung, Eingabe, Methode und Grenzen; Rauschen ehrlich behandeln. Heisse Pfade hier: Worker-Takt, `_tick_overlay` (250 ms, `ticktime`), OCR, Karten zeichnen. Keine Zeitgrenzen in CI-Tests (geteilte Runner).
- **Sicherheit.** Nie committen: Geheimnisse (Tokens, Keys, Passwörter), Laufzeitdateien (`settings.json`, Logs, `diagnose.txt`, `debug/` …) oder persönliche Daten (z. B. Spielernamen in Testbildern verpixeln, keine echten Benutzerpfade; Wächter `tests/test_repo_hygiene.py`: keine Laufzeitdateien, keine Schlüssel/Tokens in getrackten Textdateien). Ein gefundenes Geheimnis nie zitieren, Widerruf/Rotation empfehlen – Löschen im neuesten Commit entfernt es nicht aus der Historie. Prüfen, wo es passt: Eingaben und Pfade (Traversal), Subprozesse (keine Shell-Strings mit Pfaden, vgl. 1.8.45), Dateirechte, Timeouts/Grenzen, Fehlerpfade, sensible Daten in Log und Meldungen (Server-IP, Titel – siehe oben), GitHub Actions (geringste Rechte, kein privilegierter Token für Code aus PRs), Abhängigkeiten (Update erst nach Kompatibilitätsprüfung). Nur lesende Scans, nie externe Systeme angreifen; nie „vollständig sicher“ behaupten.
- **Befunde** (Audit/Review): CRITICAL / HIGH / MEDIUM / LOW / INFORMATIONAL, je mit ID, Datei + Funktion/Zeile, Beleg bzw. Reproduktion, Ursache, Auswirkung, Fix, Prüfstatus; Vermutungen nie als bestätigte Lücke. Ein volles Audit nur auf ausdrücklichen Wunsch oder bei erheblichem Risiko – sonst die Regeln auf die aktuelle Aufgabe anwenden.
- **Ablauf je Aufgabe:** Code und Regeln lesen → Arbeitsbaum prüfen → kleinste Lösung → pyflakes/pytest (+ Offscreen-Rendern bei UI) → eigenen Diff auf Regressionen und Fremdes prüfen → Bericht mit ausgeführten Befehlen, Ergebnissen, offenen Risiken. **Fertig** = Anforderung erfüllt, relevante Prüfungen gelaufen, Kompatibilität bedacht, Performance-Aussagen gemessen, Sicherheit bedacht, Doku aktuell, kein Fremdes im Diff, Restrisiken genannt.
- **Freigaben:** Pushen, PR öffnen und bei grünem CI selbst mergen bleibt dauerhaft freigegeben (Arbeitsweise unten; vom Nutzer 1.8.51 bestätigt). Nie ohne ausdrückliche Freigabe: Releases, Git-Historie umschreiben (ausser dem Zurücksetzen des eigenen Arbeitszweigs auf `main` nach dem Merge), Repository-Einstellungen, zerstörerische Operationen.
